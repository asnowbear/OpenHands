Design note · local launchers

A local Docker sandbox is offered when the daemon is up

When docker info succeeds, the host Agent Server is started with both conversation runtimes. New conversations still run on the host. Home and Settings → Runtime can put one conversation in its own container. Canvas and automation stay on the host.

1Host execution stays the default

The UI already shows Docker when /server_info lists it in available_conversation_runtimes. Launchers previously forwarded that capability only if the parent process already had OH_CONVERSATION_RUNTIME or OH_CONVERSATION_RUNTIME_SELECTABLE. This change probes Docker and, with no explicit choice, sets the selectable flag on the agent-server child.

★ The automatic default is written only into the agent-server environment. resolveBindHost still reads the parent environment, so a machine with Docker keeps 127.0.0.1 and the injected session key.

2The child env grows; the launcher contract does not

Compatibility is additive. compatibility.minimumAgentServer stays 1.59.0. No new Agent Server field. buildAgentServerEnv gains an optional dockerAvailable flag that defaults to false, so existing tests that pass { env: {} } stay host-only.

3Four launchers probe; the image entrypoint does not

probeDockerDaemonOnce runs docker info with a 5s timeout and caches the boolean. A missing binary, a stopped daemon, or a timeout leaves the host-only server and does not fail the stack.

4An explicit choice always wins

explicitChoice is true when either variable is present, including OH_CONVERSATION_RUNTIME=local and OH_CONVERSATION_RUNTIME_SELECTABLE=0. Those stay host-only even if Docker is up. OH_CONVERSATION_RUNTIME=docker stays docker-only. The pinned image is filled in only when the resolved env is Docker-capable and the image key is absent.

Tests that lock this

npx vitest run __tests__/scripts/dev-safe.test.ts __tests__/scripts/dev-with-automation.test.ts — 184 passed. The new cases cover auto-select plus pinned image, opt-out, a custom image left in place, a failed docker info, and loopback bind with the session key still injected.

5A Docker conversation may not reach host ingress

⚠ Containers reach host services through host.docker.internal. That path needs the ingress on 0.0.0.0, which today happens only when the parent env sets OH_CONVERSATION_RUNTIME=docker or OH_CONVERSATION_RUNTIME_SELECTABLE=1 (resolveBindHost). The automatic default deliberately does not do that, so tool execution inside the container works, and callbacks to ingress or automation on the host do not, until the operator sets one of those variables or OH_BIND_HOST.

The first Docker conversation also pulls the pinned agent-server image. Startup of Canvas itself does not wait on that pull.
